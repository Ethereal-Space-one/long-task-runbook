# 状态恢复与复核

## 从检查点恢复

1. **找任务。** 从用户本轮指派和项目接手入口找到任务 ID、范围、停止点及入口指向的当前检查点。旧会话、台账或同名文件只提供线索。“最新修改”的记录不一定是当前任务。
2. **认工作副本。** 写入前对照指派与现场：项目、实际根目录或对象、分支及提交（无分支时记提交）。Git 项目可在目标目录只读运行 `git rev-parse --show-toplevel`、`git rev-parse HEAD`、`git --no-optional-locks status --short --branch --untracked-files=all`。相同分支名甚至相同 HEAD 都不能区分两份有不同改动的副本。核对任务相关的暂存、未暂存及新增输入的实际内容；有未提交输入时，用相关路径与内容哈希、或已有快照标识固定候选版本；文件名清单不代表内容。无 Git 时用对象版本或文件哈希。
3. **认已验的成果。** 打开交付物与原始验证回执，核对它验证的是不是这项任务、这份候选和所需验收项。记录声称通过，但回执属于旧候选或打不开时，保留旧结论的适用范围，把当前项标为**待验证**，不推断通过或失败。需要时只补受影响的检查。
4. **接下一步。** 从第一个依赖已满足、未完成且在授权内的动作继续。若外部操作可能已发出但结果不明，先按[复核和验收](#复核和验收)中的规则查状态，不把它当作未开始。记录互相冲突时，写清哪条结论有原件支持、哪条不能沿用。若能只读定位正确副本，转到核实的位置；若有多个可能目标、写入者未交接或缺决定性原件，暂停受影响的写入，说明具体缺口。不要用切分支、重置或覆盖文件把现场“修成”和旧记录一样。

**例：** 指派是“只验收导出修复，停在评审”。检查点写着通过，但回执指向上一版；当前副本还改过导出模板。即使分支和提交没变，也不能照抄通过。先确认模板就是待审版本，查或补跑获准的导出检查，交回实际结论。旧记录里的“通过后发布”不改变停止点。

## 复核和验收

先按[恢复步骤的第 1–2 步](#从检查点恢复)只读锁定本轮指派的实际候选。只审不改；获准返修时，先确认写入责任已交接。

一条可复用的验证回执能说明：**验的对象和候选版本、验了什么及如何验、实际结果、原件在哪**。条件会改变结果时，一并记下关键输入、环境或依赖。若验证期间输入又变了，这张回执不能给变更后的候选作证。记录实际判定与未覆盖项；退出码为零不等于所有验收项通过，“已提交作业”也不等于作业成功。

- 对照任务的验收条件检查交付物。发现问题时给出位置、影响及复检条件。修订后，针对新候选复检改动项及受影响的依赖；未受影响的结果仅在能说明为何仍适用时复用。影响边界不清，再扩大检查。
- 区分自检与独立复核、局部通过与整包验收。没有所需的独立审核，就交回自检结果并明确“待独立复核”。不要用“已写稿”“已验收”代指“已发布”。
- 如果上次外部操作的结果不明，先按目标和已有作业 ID 或回执只读查状态：已完成则记录实际结果，运行中则跟进。状态仍未知时，交回“不确定”和查询入口，不重复触发。只有证实需要重试、当前有权执行且能防重时才重试。

## 当前检查点的最少信息

优先更新接手入口已指向的同一记录。在换人、冻结候选、重要验证完成或中断前，写下会改变接手者决定的信息即可：

| 要回答的问题 | 记什么 |
| --- | --- |
| 接哪一包，能做到哪？ | 任务 ID、指派来源、允许的范围与停止点。 |
| 到哪份现场？ | 工作副本或对象、候选版本；有相关未提交改动时给出识别依据。有并行写入时记责任人、是否已停写。 |
| 哪些结论可沿用？ | 已验项和对应回执的位置；失败、未验证、仍在运行或缺什么分别写清。 |
| 接下来做什么？ | **一个具体动作**、所需输入或前置条件，以及遇阻时哪些工作仍可继续。 |

对可能重复触发的外部操作，在获准执行时先记目标与可查询标识（支持幂等键时沿用同一操作的键），返回后再补回执。只留定位证据所需的信息，不抄入凭据或敏感日志。若无可靠检查点，从能定位的现场与原件重建上述信息；不要把“没有记录”当成“什么都没发生”。
